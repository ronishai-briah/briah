# בריא.ה — אפליקציית חברות ומלוות (מודול 1)

יישום של **שלב 1** מתוך `docs/briah-app/vision-and-roadmap.md`: מודל ההרשאות, לוח מלווה, הערות עם toggle נראות, וסעיף דיווח/תנאי העסקה/תשלום מתרגלים. ראו `docs/briah-app/dev-brief.md` לספק המלא.

## הרצה

```bash
cd member-app
npm install
npm run dev      # http://localhost:5173/member-app/
npm test         # מריץ את בדיקות מנוע ההרשאות
npm run build
```

בכניסה תתבקש/י לבחור "מי נכנס/ת" — זה **לא** מסך התחברות אמיתי, ראו "מה מדומה" למטה.

## החלטות ארכיטקטורה שנעשו כאן (לא אושרו איתך מראש — ניתן לשנות)

הבריף השאיר כמה בחירות פתוחות ("Claude Code יכול להמליץ") ושאלות שלא נענו בזמן. אלו ההחלטות שנלקחו כדי להתחיל לבנות:

1. **תיקייה נפרדת בתוך אותו ריפו** (`member-app/`), לא ריפו חדש — האפליקציה הזו שונה לגמרי מכלי הגאנטים שכבר קיים בריפו (`src/` בשורש), אבל אין סיבה טובה עדיין להפריד לריפו נפרד.
2. **TypeScript + React + Vite** (בניגוד לכלי הגאנטים שהוא JS רגיל) — מנוע ההרשאות הוא הליבה של המוצר הזה, וטיפוסים תופסים בדיוק את הבאגים המסוכנים ביותר כאן ("מי רואה מה").
3. **פלטפורמה: web רספונסיבי**, לא native/PWA בשלב הזה — הכי מהיר לבנות ולתחזק, ועובד גם בנייד וגם בדסקטופ מהיום הראשון. אפשר להוסיף PWA manifest בהמשך בלי לשנות ארכיטקטורה.
4. **Backend מתוכנן ל-Supabase** (Postgres + Auth + Storage) — הסכמה וה-RLS ב-`supabase/migrations/0001_init.sql` ממופים אחד-לאחד למטריצת ההרשאות. **עדיין לא מחובר בפועל** — אין לי (Claude) חשבון Supabase; זה ממתין למפתחות שרוני תמסור ישירות לסביבת הפיתוח, באותו אופן שתואר לגבי מפתח ה-API של ארבוקס.

## מה עובד עכשיו (ניתן להריץ ולנסות)

- **מנוע הרשאות** (`src/domain/permissions.ts`) עם 15 בדיקות (`npm test`) שמאמתות אותו מול כל שורה במטריצה ב-`docs/briah-app/permissions-model.md`.
- **לוח מלווה**: רשימת חברות משובצות, מיון לפי "כדאי להתעדכן" (אין הערה מעל 3 שבועות), כרטיס חברה עם תוכנית אישית + הערות מסוננות לפי הרשאה + טופס הוספת הערה עם toggle נראות ודגל "קריטי" (רק למתרגל/ת).
- **מסך מתרגל/ת**: תנאי העסקה שלו/ה בקריאה בלבד, טופס דיווח חודשי עם צירוף קבלה, רשימת הדיווחים שלו/ה עם סטטוס תשלום.
- **מסך ניהול (Owner)**: הגדרת/עריכת תנאי העסקה לכל מתרגל/ת, סקירת כל הדיווחים וסימון שולם/לא שולם/שולם חלקית עם הערה.
- החלפת "מי נכנס/ת" מדגימה בבירור איך אותה חברה נראית אחרת לכל תפקיד (למשל: מנחה סדנה לא רואה הערה "מוגבלת" שלא שותפה איתו; מתרגל לא רואה תנאי העסקה של מתרגל אחר).

## מה מדומה/חסר עדיין (חשוב לדעת לפני שמכניסים נתונים אמיתיים)

| מה | מצב היום | מה צריך כדי לסגור |
|---|---|---|
| התחברות (Auth) | "בחר/י מי את/ה" — כל אחד יכול להתחזות לכל משתמש/ת | חיבור Supabase Auth אמיתי (מייל+סיסמה/מג'יק לינק) |
| שמירת נתונים | `localStorage` בדפדפן בלבד — כל מכשיר/דפדפן רואה עותק אחר, שום דבר לא משותף בין אנשי צוות בפועל | חיבור ל-Supabase Postgres (הסכמה כבר כתובה, `supabase/migrations/0001_init.sql`) |
| קבצים/קבלות | נשמרים כ-base64 בתוך ה-localStorage — לא בר-קיימא, לא מתאים לקבצים גדולים | Supabase Storage |
| ארבוקס | **לא מחובר בכלל** — אין עדיין מסך בית, לוז, סטטוס מנוי (P0 #1-2) | מפתח API מארבוקס (ראו `docs/briah-app/arbox-integration.md`) + adapter שממפה את ה-endpoints ל-`AppData` |
| כתיבה למלווה (חברה → מלווה) | לא נבנה עדיין (P0 #3) | תלוי בהחלטה על מסך "חברה" עצמו — עדיין persona עתידית לפי הבריף |
| טופסי הסכמה | לא נבנו | תוכן משפטי מיולה (ראו open questions ב-`docs/briah-app/dev-brief.md`) |
| נתונים בדמו | שמות עובדים אמיתיים (מהבריף) אבל **כל התוכן שלהם בדוי** — אין נתון אמיתי אחד על אף חברה | להחליף לגמרי לפני production |

## המבנה

```
src/
  domain/       טיפוסים + מנוע ההרשאות (permissions.ts) — מקור האמת היחיד ל"מי רואה/כותב מה"
  data/         seed.ts (נתוני דמו) + store.tsx (state בזיכרון + localStorage, ל-Context)
  features/
    auth/       מסך "מי נכנס/ת" הזמני
    mentor/     לוח מלווה + כרטיס חברה
    practitioner/  תנאי העסקה + דיווח חודשי
    owner/      ניהול תנאי העסקה + סקירת תשלומים
supabase/
  migrations/0001_init.sql   סכמת Postgres + RLS, טרם הורצה מול פרויקט אמיתי
```

## הצעד הבא (לפי סדר העדיפויות בבריף)

1. **כתיבה למלווה + מסך בית לחברה (P0 #2-3)** — הפרסונה של "חברה" עדיין לא קיימת באפליקציה בכלל.
2. **חיבור Supabase אמיתי** — להחליף את `src/data/store.tsx` מ-localStorage ל-`@supabase/supabase-js`, להריץ את המיגרציה, ולהוסיף Auth אמיתי. דורש שרוני תיצור פרויקט Supabase ותמסור URL+key לסביבת הפיתוח.
3. **חיבור ארבוקס (P0 #1)** — דורש מפתח API מרוני. כדאי לבנות כ-adapter מבודד (interface אחד, מימוש mock קיים + מימוש אמיתי) כדי שהמסכים לא ידעו אם המידע מגיע ממוק או מארבוקס אמיתי.
4. **החלטות פתוחות שכדאי לסגור לפני עוד בנייה** (מפורט ב-`docs/briah-app/dev-brief.md` סעיף 11): האם רוני רואה תוכן הערות טיפוליות עצמו, תוכן טופסי ההסכמה, והאם מנחה סדנה קבוצתית בכלל כותב הערות (כרגע ההנחה באפליקציה: לא).
